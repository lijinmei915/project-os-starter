# Memory 维护规则

> 用途：定义什么该进 memory、什么时候更新、怎么写得简洁稳定。
> 什么时候更新：当全局记忆策略、项目/用户边界或长期记忆格式发生变化时更新。
> 不要写什么：不要写本轮流水账、一次性讨论或仓库里已经有 SSOT 的细节。

## 该记什么

- 稳定的项目事实：项目目标、阶段、关键路径、长期约束
- 稳定的用户偏好：沟通风格、协作习惯、明确纠正过的工作方式
- 稳定的流程约束：例如“先测再推”“改前先给方案”
- 会影响后续判断的重要背景：长期未完事项、关键依赖、明确禁区

## 不该记什么

- 一次性的临时讨论
- 已经过时的假设
- 可以从仓库文档直接读到的细节
- 零碎执行日志

## 什么时候更新

- 用户明确纠正了工作方式
- 项目阶段发生变化
- 新增了长期有效的规则或禁区
- 一次错误复盘后形成了稳定约束

## 怎么写

- 一条只写一个稳定事实
- 用短句，不写流水账
- 优先写“事实 / 约束 / 影响”
- 不确定的内容不要写进 memory

## 推荐分层

- `project_*.md`：项目事实与阶段
- `user_profile.md`：用户背景与长期偏好
- `user_preferences.md`：称呼、回答风格、解释深度等全局映射
- `feedback_*.md`：具体协作反馈与收尾规则

## 全局与项目的边界

- 全局用户层：跨所有项目都成立的信息，如称呼、职业、技术/设计理解深度
- 项目覆盖层：只在当前项目里生效的特殊要求，写在项目内 `AGENTS.md`、`PROJECT.md` 或 `HANDOFF.md`
- 项目特征层：产品现状、阶段、决策、缺口，写在项目文档里

备注：
- 能写在项目仓库 `docs/` 里的，优先写仓库文档，不要只留在 memory。
- memory 是“长期记忆”，不是“本轮笔记”。
