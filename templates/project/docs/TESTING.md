# 测试与验收

> 用途：定义测试分层、验收标准和收尾检查。
> 什么时候更新：测试策略、验收标准、测试命令变化时。
> 不要写什么：当前项目状态、交接流水、长期产品路线图。

---

## 测试分层

### 1. 文档健康检查

确认核心文档存在且有实质内容（不是空模板/纯占位符）。

检查项：
- `AGENTS.md` / `PROJECT.md` / `HANDOFF.md` 是否存在且可用
- `README.md` / `docs/*` 是否与当前项目状态一致
- 是否残留 `{{...}}`、无解释的 `TODO`、`.DS_Store`

### 2. 行为验收

确认 AI 助手按协作流程工作。

检查项：
- 新项目是否先问项目定位，再问技术栈
- 老项目是否先判断现状，再给建议
- 用户说"跳过"时是否保留 `TODO:` 而非编造答案

### 3. 代码测试

确认业务代码有基本验证。

建议：
- 纯函数、解析、权限判断 → 单元测试
- 关键用户流程 → 端到端或手测清单
- API 请求 → 至少验证成功、失败、loading 三种状态

### 4. AI 生成代码验收

确认 AI 生成或大幅改写的代码没有只“看起来能跑”，而是能被测试和回归。

检查项：
- 新增工具函数、解析逻辑、权限判断必须有单元测试，或说明暂不测试的原因
- API / 工具调用至少覆盖一个成功用例、一个失败用例和一个边界用例
- UI 改动需要覆盖主要交互状态：默认、hover、focus-visible、loading、错误或空态
- AI 生成代码提交前必须运行与改动相关的测试命令，不用未验证的猜测代替测试结果
- 如果测试暂时不可运行，必须在 `HANDOFF.md` 记录原因、风险和下一步

### 5. 设计一致性

确认 UI 改动没有偏离设计规范。

检查项：
- 改 UI 前是否读过设计规范
- 新组件是否复用已有 token 和 pattern
- 可点击元素是否有 hover / focus-visible 状态


## 收尾最小检查

每次主要改动后确认：
- 改动是否符合当前阶段目标
- UI 改动是否符合设计规范
- 代码改动是否运行了测试
- 下一步如有变化，是否更新了 `HANDOFF.md`
- 踩坑后是否更新了 `docs/LESSONS.md`
