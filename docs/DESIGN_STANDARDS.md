## 2. 组件分层

| 分层 | 含义 | 规则 |
|------|------|------|
| Primitive | {{shadcn 原语 / MUI / 项目基础组件}} | 优先复用，不再维护第二套基础组件 |
| Pattern | 本项目的业务组合、布局节奏、状态规则 | 在 Primitive 之上封装，只补业务语义 |
| Page | 当前页面自己的布局、状态切换和内容编排 | 不提前抽复用，先服务好当前页面 |

快速判断：

- `Primitive`：脱离业务也成立，如 `Button`、`Input`、`Dialog`
- `Pattern`：开始表达业务语义，如"保存表单""错误提示区"
- `Page`：只属于当前页面的整体结构和状态切换，先留在 Page，稳定后再看是否上提

结论：

- 能直接用基础组件库的，先用基础库
- 需要项目节奏、业务排序、业务状态时，再上 Pattern
- 只在当前页面成立的结构，先留在 Page
- 不允许因为视觉偏好随意新造 primitive

## 3. 总规则

### 3.1 Token 优先

- 颜色、圆角、阴影、文字层级优先走 token
- 禁止在组件里硬编码视觉值，如 `#333333`、`text-[#262626]`
- 组件例外色只能留在组件自己的语义槽位中，不能跨组件复用

### 3.3 一致性优先

- 同一组内，表达方式必须统一，不要一半用图标、一半只用文字
- 图标默认跟随父级 `currentColor`，不单独再造一套颜色
- 同功能按钮优先按一组处理，组内节奏、分隔线和状态表现要一致
- 一套规则一旦稳定，就优先并回 token、primitive、pattern 或总规范，不保留第二份重复文档

### 3.2 结构先于装饰

- 先保证层级对、信息顺序对、状态位置对，再考虑"好不好看"
- 不要为了"显得完整"给普通输入区额外套无意义壳层
- 没有明确分组意义时，优先直接展示组件，不额外加卡片壳

### 3.3 主流程优先

- {{产品的核心路径}}（例如"保存""下单""提交"）优先级高于辅助功能
- 辅助功能（AI、推荐、自动填充等）失败、超时，不得阻塞主流程
- 辅助状态提示必须是"辅助信息"，不能压过主操作

### 3.4 文案位置固定

- 输入错误：放输入框下方
- 局部 AI / 辅助状态：放对应标题右侧或局部说明位
- 底部操作区说明：只放主操作相关结果、进度、失败原因
- 不要把输入错误塞到底部统一灰字里

## 4. 颜色与文案速查

| 场景 | 文案位置 | 颜色 / class |
|------|----------|--------------|
| 表单错误（无效输入、重复） | 对应输入框下方 | `text-destructive` |
| 轻警告（超时、失败、重复） | 局部说明位 | `text-[var(--warning)]` |
| 辅助说明 | 字段下方或底部说明区 | `text-muted-foreground` |
| 进行中 | 标题右侧 | `text-muted-foreground` + loading 图标 |

## 5. 布局与间距总原则

- 表单字段默认按"标题在上，内容在下"排
- 同级字段之间保持统一垂直节奏，优先 `space-y-4`
- 标题与字段内容之间优先 `mb-1`
- 标题右侧轻操作默认小字号、弱色，不抢主视觉
- 已选项、推荐项、错误提示都应贴着对应输入区，不要飘到别的区块
- 间距先按等级选，不按页面感觉随意写值；等级定义见 `docs/design/tokens.md`
- 容器内边距和内部模块间距要分开判断，不要把所有留白都堆在一个 `space-y` 上

## 8. 同步规则（强制）

- 新增共享组件时，必须同时：
  - 新建或更新 `docs/design/*.md`
  - 更新 {{showcase / storybook / 组件索引}}
- 改了组件命名、定位、分层后，文档和 showcase 必须同轮同步
- 任何一次 UI 纠偏，如果形成稳定规则，必须回写设计文档
- **双向强制**：改了 showcase 结构 → 当轮必须更新对应文档；改了文档结构 → 当轮必须更新 showcase

## 10. 一句话原则

{{PROJECT_NAME}} 的 UI 规范目标不是"写一份大而全手册"，而是让任何协作者在遇到具体场景时，都能快速知道：

- 用哪一层
- 查哪份文档
- 这个场景应该怎么做
- 哪些做法不能做
