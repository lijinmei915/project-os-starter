# Project OS 产品规划

> 这份文档回答的是：这个项目接下来往哪走、这个阶段先做什么、为什么这么排。
> 它是路线图，不是项目定义，也不是当前回合交接。

**最后更新**: 2026-05-06

---

## 产品愿景

把 AI 驱动开发流程收口成一个可复制、可验证、可交接的 Project OS。

它的目标不是直接生成某个业务产品，而是先稳定 AI 如何理解项目、分流任务、遵守规则、记录状态和接受测试。

## 当前阶段目标

稳定 v1 内核：让项目级请求、设计规范请求和前端页面请求能进入明确流程。

## 阶段策略

先收口内核，再清理文档，最后再评估组件层。

---

## 近期规划（2-6 周）

### 本阶段要做

| 方向 | 目标 | 说明 |
|------|------|------|
| v1 路由 | 保持 7 条核心 case 稳定通过 | 这是 Project OS 能否作为入口的基础 |
| docs 清理 | 删除旧模板残留，统一 SSOT | 避免 README / AGENTS / PROJECT / HANDOFF 职责冲突 |
| 校验机制 | 保持 `check-runtime.sh` 可用 | 先做轻量体检，不急着上复杂自动化 |

### 本阶段不做

- 不接 Radix / shadcn / ai-components
- 不新增外部 skill 依赖
- 不做自动自进化
- 不生成真实业务页面

### 当前优先级

1. 清理 `docs/` 旧模板残留
2. 保持 v1 路由测试 7/7 pass
3. 做小步 commit，避免规则漂移

## 中期规划（1-3 个月）

| 方向 | 价值 | 前置条件 |
|------|------|---------|
| 组件层选型 | 让 AI 能稳定生成可用 UI | v1 路由和设计规则稳定 |
| ai-components | 给 AI 一个可控组件调用面 | 先决定 Radix / shadcn / 自研封装边界 |
| 自动化测试 | 降低人工复测成本 | CLI 测试格式稳定，登录态可控 |

---

## 长期方向（3-6 个月+）

| 方向 | 说明 |
|------|------|
| Project OS 模板化 | 能复制到新项目，作为 AI 开发底座 |
| Skill 治理 | 有 registry、tests、changelog、evidence，做到可回滚 |
| 工程化 UI | 在不牺牲可控性的前提下接入组件库和设计系统 |

---

## 为什么这样排

- 当前最容易出错的是 AI 路由，而不是组件实现。
- 组件库过早接入会把问题从入口不稳扩散到 UI、依赖、构建、设计规则都不稳。
- 先让 Project OS 自身可验证，后续接组件才有稳定边界。
