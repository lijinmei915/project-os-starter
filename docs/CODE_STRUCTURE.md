# 代码结构说明

> 用途：定义代码和目录怎么分层、各目录放什么、不该放什么。
> 什么时候更新：目录职责、分层边界、模块归属或结构约束变化时。
> 不要写什么：当前任务交接、详细变更历史、与结构无关的产品说明。
> 本文件只管代码怎么分层、各目录放什么、不该放什么。
> 默认以“职责规则”为主，不强绑某个具体项目的路径结构。

## 使用方式

- 先看分类规则，再看各类职责
- 如果老项目已经有更成熟的结构说明，优先沿用或轻量收口
- 如果当前项目还没有稳定结构，可以只保留通用规则，不强行补完整示例

## 可插拔规则

- 本文件本身是可选增强文档，不是核心入口
- 文档重点是“职责怎么分”，不是“文件名必须长什么样”
- “本项目示例”部分是可选的：存在就读，不存在就跳过

## 分类规则

- 先按职责域分类，不按技术名词分类
- 越靠前的层级越通用、越稳定、越可复用
- 越靠后的层级越接近具体业务和具体页面
- 如果一个目录同时像两类，优先看它主要服务谁
- 新目录只有在现有分类承接不了时才新增

## 分类总览

### 1. Token（设计令牌）

职责：
- 承接全局样式变量、设计 token、基础样式入口

例如：
- `src/styles/`

不该放：
- 组件内部专属样式实现
- 带强业务语义的视觉规则

### 2. Primitive Components（基础组件）

职责：
- 承接可复用 UI 原语

例如：
- `src/components/primitive/`

不该放：
- 业务流程
- 接口调用
- 强业务状态判断

### 3. Layout（布局）

职责：
- 承接页面骨架、导航、壳层

例如：
- `src/components/layout/`

不该放：
- 具体业务表单逻辑
- 强绑定某个单一业务流程的组合组件

### 4. Pattern Components（业务组件）

职责：
- 承接业务组合、表单、列表、业务 pattern

例如：
- `src/components/patterns/`

不该放：
- 底层工具函数
- 完全通用的 UI 原语

### 5. Page（页面）

职责：
- 承接页面级组件、路由入口

例如：
- `src/pages/`

不该放：
- 可跨页面复用的小组件
- 脱离页面也能成立的业务组合

### 6. Logic（逻辑能力）

职责：
- 承接状态逻辑、业务工具、通用能力

例如：
- `src/hooks/`
- `src/utils/`
- `src/lib/`

#### hooks

放什么：
- 可复用状态逻辑、订阅逻辑

不放什么：
- 页面私有的小变量整理
- 纯工具函数

规则：
- 只有复用价值明确时再抽成 hook
- hook 名称用 `useXxx`
- hook 返回值尽量稳定、语义清晰
- 页面里只用一次、且没有复用潜力的状态，不必急着抽 hook

#### utils

放什么：
- 业务工具、数据访问、格式转换

不放什么：
- UI 组件
- 完全底层、跨业务的库封装

规则：
- 输入输出要清楚，副作用尽量集中
- 远程请求要有错误处理和 loading 策略
- 如果已经明显带业务语义，不要伪装成 `lib`

#### lib

放什么：
- 通用能力、第三方库封装

不放什么：
- 强业务语义代码

规则：
- 如果离开当前项目也依然成立，才更像 `lib`
- 不要把业务判断藏进 `lib`

### 7. Scripts（工程脚本）

职责：
- 承接构建辅助、校验、生成脚本

例如：
- `scripts/`

不放什么：
- 线上业务代码

规则：
- 脚本用途要能从文件名看出来
- 会影响线上资源的脚本要写清输入输出
- 脚本和业务代码边界要清楚，不要互相侵入

### 8. Backend / Data（后端 / 数据，可选）

职责：
- 承接服务端逻辑、接口层、数据库层

例如：
- `api/`
- `server/`
- `db/`
- `supabase/`
- `prisma/`

说明：
- 这一类不是所有项目都需要
- 只有项目里真的有后端 / 数据层时，才补这部分结构说明

## 什么时候需要新增目录

- 现有目录已经放不下，而且职责边界明确
- 新目录能长期存在，不是为一次性需求临时加的
- 新目录命名能表达职责，而不是只表达技术名词
