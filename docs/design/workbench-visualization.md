# 工作区可视化规范

> 用途：定义 OmniDesk 左侧工作区每个菜单下的页面应该怎么可视化、怎么放状态、怎么放动作、怎么处理空态和风险。
> 什么时候更新：工作区菜单职责、页面视觉结构、工作面组件模式或可视化验收规则变化时。
> 不要写什么：单次页面实现流水、临时截图反馈、具体业务文案全文、未确认的新功能路线。

本文是 `项目流程 / 任务执行 / 知识记忆 / 工程资产 / Agent 配置` 下所有工作面的可视化规范。

核心目标：

```txt
每个菜单都必须让用户一眼知道：
当前是什么状态 -> 为什么是这个状态 -> 下一步能做什么 -> 相关证据在哪里
```

---

## 总原则

1. **工作面不是文档页**
   - 不以大段说明文字作为主体。
   - 说明文字只用于解释状态和动作，不替代状态可视化。

2. **每个菜单必须有主视觉结构**
   - 不能只显示 `治理角色 / 状态来源 / 更新时机`。
   - 治理元信息放在页面底部或折叠区域，主区域优先展示真实状态。

3. **先状态，再动作，再证据**
   - 状态在顶部。
   - 主要动作在首屏可见。
   - 证据文件、日志、报告放在底部，可点击预览。

4. **同类菜单同类结构**
   - 生命周期类页面用进度型结构。
   - 任务类页面用任务详情 / 队列结构。
   - 资产类页面用健康矩阵 / 文件列表结构。
   - 配置类页面用连接状态 / 能力矩阵结构。

5. **少卡片、强分区**
   - 页面区域使用全宽分区和栅格。
   - 卡片只用于重复项、任务项、文件项和配置项。
   - 不在卡片里再套卡片。

## 页面骨架

治理页面头部使用固定结构：

```txt
页面名称                         当前状态 + 唯一主操作
一句话说明页面回答什么
更新时间 · 主要来源
```

规则：

- 页面名称使用 18px 紧凑标题，不使用 Hero 尺寸。
- 说明只能有一行主句，更新时间和来源作为弱元信息。
- 状态只表达本页当前结论，如 `已接入 / 进行中 / 待确认 / 需处理 / 不可用`。
- 头部最多一个主操作；不需要动作时不留占位。
- 不在头部放重复栏目 Badge、统计数字、文件路径、治理角色或多个按钮。
- 项目概览作为首个标准实现：头部标题使用 20px 项目名称，版本号使用中性 `Badge` 标签，更新时间精确到秒并作为弱元信息依次紧跟标题右侧；下方的一句话介绍独占整行，不受右侧状态与操作挤压；来源区占满整行，所有事实来源以灰色可点击标签完整展开，hover / focus 底色加深，点击进入只读文件预览。状态显示来自 `.omnidesk/data/state.json` 的固定生命周期阶段：`启动中 / 打磨中 / 交付中 / 维护中 / 已归档`。事实最新时不显示常驻文字主操作，只保留带 Tooltip 的弱刷新图标；检测到变化或更新失败时才显示 `立即更新 / 重试` 主操作。

所有菜单工作面使用同一套骨架：

```txt
Workspace Surface
  Header
    Title
    One-line State Summary
    Primary Badge / Status
  State Visual
    Progress / Health / Connection / Queue / Matrix
  Primary Actions
    1-3 个当前可做动作
  Main Content
    最近完成 / 下一步 / 文件状态 / 配置项 / 结果列表
  Evidence
    关联文件、报告、运行记录，可点击只读预览
  Governance Meta
    治理角色、状态来源、更新时机、下一步治理动作
```

规则：

- Header 不超过两行说明。
- State Visual 必须在首屏出现。
- Primary Actions 最多 3 个，更多放入 `高级详情` 或二级菜单。
- Evidence 必须可点击，只读预览，不直接编辑。
- Governance Meta 不能占据页面主视觉。

## 工作面类型

### 0. Portfolio / Action Surface

适用：

- `工作台`

工作台位于单项目之上，是跨项目的判断与行动中枢，不是统计大屏或项目列表页。

结构：

```txt
今日工作 + 全局主操作
需要处理（失败 / 阻塞 / 等待确认）
项目状态与当前动作
AI 工作队列
最近关键活动
```

必须包含：

- 10 秒内可判断哪个项目需要处理、原因和下一步。
- 可在工作台内发起任务、添加项目、切换项目和进入待处理任务。
- 切换项目后仍停留在工作台；只有用户明确打开任务或证据时才进入详情。
- 空态给出“当前无阻塞事项”的结论，不留空卡片。

禁止：

- 用项目总数、可用数等低行动价值统计占据首屏。
- 默认展示项目路径、registry 来源或内部执行流水。
- 在工作台重复展示关联工程文件和治理元信息。
- 切换项目后自动离开工作台。

### 1. Progress Surface

#### Project Overview Surface

`项目流程 / 认识项目 / 项目概览` 使用固定的项目认知结构，不复用工作台或任务看板：

```txt
项目头部：项目名称 / 版本号 / 更新时间 / 一句话介绍 / 生命周期阶段 / 来源
核心定位：产品目标 / 核心能力
技术组成：应用框架 / UI 组件 / 工程工具
工程结构：应用代码 / 治理与文档 / 构建与质量
```

边界：

- 项目概览回答“这个项目是什么、为什么做、怎么组成、目前在哪个阶段”。
- 项目名称和一句话介绍只出现一次，不再追加独立“项目身份”头部。
- 分区副标题紧跟主标题右侧，不放到分区最右侧；分区标题到内容统一为 8px。
- 分区存在 `查看详情` 类下钻动作时，动作放在标题行最右侧，不作为正文第三列。`技术方案` 使用 `查看架构详情` 作为标准实现。
- 概览型分区统一使用 `OverviewSection`：接受标题、副标题、右侧 `actions` 插槽和 1–3 个 `items`。内容项按实际数量自动等分；只有 1 项时隐藏列内小标题，直接展示正文。右侧插槽可放查看详情、刷新、生成任务等本分区动作，不影响内容列数。
- 项目概览不设独立“当前状态”指标行：生命周期阶段已在头部展示，当前目标、项目接入和治理健康分别回归当前进度、项目接入和治理报告页。
- 项目概览不展示“已确认事实 / 待确认事实 / 信息来源 / 最近扫描”等内部统计；来源和更新时间已由头部承载，事实完整度只有在能解释缺口并提供补齐动作时才进入专门工作面。
- 项目概览不追加详情入口导航；左侧工作区菜单是治理页面的统一入口，概览不重复一组没有状态摘要的链接。
- 项目概览采用“固定骨架 + 可选分区”：项目头部和核心定位固定展示；技术组成、工程结构、依赖、业务模块等只在存在可信内容时渲染。`待补充 / 待识别 / 尚未记录` 不得作为概览占位内容，缺失事实进入项目档案或更新事实流程。
- 可选分区内容较少时按 1–3 列自动均分；内容较多时概览只展示分类摘要和一个详情入口，不在概览无限扩展字段。不同项目可以拥有不同数量的可选分区，但分区顺序由统一 registry 决定，禁止页面内临时拼接。
- 正文分区按实际内容使用一至两列；列间距 16px，每列小标题到正文为 6px，分区标题到小标题的实际总间距为 8px，分区与分区的实际总间距为 `--desktop-space-overview-section`（当前 20px）。所有使用 `OverviewSection` 的专属概览页必须挂载 `.overviewSurface`，由该容器统一提供页头到首分区、以及分区到分区的纵向间距；各列自身不再增加上下或左右 padding，避免与容器 gap 叠加。
- 技术与目录数组不得直接使用斜杠平铺。技术按 `应用框架 / UI 组件 / 工程工具` 分类，目录按 `应用代码 / 治理与文档 / 构建与质量` 分类；组内使用无交互态的实心中性 Tag，Tag 文字使用最高层级正文色，目录 Tag 使用等宽字体。可点击来源不得与静态 Tag 同形，统一使用文件图标、透明底和 hover 反馈的链接按钮。
- 任务、预警、最近活动和下一步行动归工作台，不在项目概览重复。
- 状态只展示一层摘要；详情和证据进入对应治理页面。
- 项目概览只保留项目事实刷新能力，不承载批量修复、清理产物或任务执行动作。事实最新时该能力降级为 `重新扫描项目` 图标按钮；只有检测到变化或需要失败恢复时才升级为文字主操作。
- 项目事实更新不得在正文追加成功提示条；更新时间旁承担 `检测到变化 / 正在更新 / 已更新 / 更新失败` 状态。成功后同步刷新时间并隐藏主操作；自动或手动失败都必须按项目保存失败时间、原因、变化签名和重试次数，重载后继续显示错误和 `重试`，不得定时恢复成无错误状态，也不得自动无限重试。事实新鲜度、变化来源和上次成功时间仍以 `.omnidesk/data/fact-freshness.json` 为准，失败恢复记录不能成为第二套事实源。
- 不在项目概览底部追加通用治理元信息和关联文件列表。

适用：

- `项目流程 / 当前进度`
- `定义目标 / 当前目标`
- `验证交付 / 验收报告`
- `复盘沉淀 / 交接记录`

结构：

```txt
OverviewPageHeader：页面名 / 更新时间 / 一句话摘要 / 弱证据元数据
OverviewSection：项目位置（当前里程碑 + 当前目标）
OverviewSection：目标阶段（目标定义 → 任务拆解 → 执行推进 → 目标验收 → 完成确认）
OverviewSection：验收与风险（验收标准 + 最近验收 + 项目风险）
OverviewSection：下一步（唯一项目级建议）
```

必须包含：

- 当前项目里程碑和当前目标
- 目标阶段链，不用任务完成数计算项目百分比
- 与当前目标 ID 匹配的验收标准和验收结果
- 项目风险摘要
- `下一步`
- 汇总来源数量、状态或更新时间
- 与项目概览共用 `OverviewPageHeader` 和 `OverviewSection`，但不复用项目概览的业务 slot。

交互：

- 点击当前目标进入 `当前目标`。
- 点击当前目标、验收标准、验收结果和项目风险，分别进入其唯一 owner 页。
- `下一步`保留唯一项目级主建议。验收标准等必填项缺失时只显示缺口说明，不提供详情跳转；当该项已关联当前目标时，才可进入其 owner 页查看详情。
- 当前进度不在本页展开所属页面的详情或操作。

#### Current Goal Surface

`定义目标 / 当前阶段目标` 只回答“项目目标下本阶段要达成什么、覆盖什么、现在下一步做什么”。

```txt
OverviewPageHeader：当前状态 / 更新时间 / 来源
OverviewSection：目标定义
OverviewSection：范围边界
OverviewSection：下一步
```

边界：

- 对话和终端是阶段目标的主要输入入口，当前阶段目标页是确认后目标的汇总与治理 owner，不要求用户先在页面手工新建。
- 只有桌面模型真实调用成功且 provider 状态为 `available` 时，对话才可从用户表达中生成阶段目标候选；浏览器预览和模型不可用状态不得用固定模板伪造候选。
- 阶段目标候选只读展示，必须经用户点击“确认登记为阶段目标”或用明确短句确认后，才写入目标数据并自动关联当前活动项目目标。
- 确认阶段目标只写治理状态，不自动创建任务或执行代码；任务拆解继续遵守本页预览、用户确认后写入 `任务执行` 的边界。
- 任务拆解和任务执行归 `任务执行`。
- 当目标处于“待拆解”时，本页可预览并确认任务拆解草案；确认后写入关联任务并将目标更新为“待开始”，后续推进统一进入 `任务执行`。
- 验收条件和验收结果归 `验收标准`、`验收报告`。
- 已完成目标归 `目标历史`。
- 当前阶段目标不复制任务详情、队列或执行操作。

#### Acceptance Criteria Surface

`定义目标 / 验收标准` 只回答“完成要满足什么条件、当前验收结论是什么”。

```txt
OverviewPageHeader：验收状态 / 更新时间 / 来源
OverviewSection：关联目标
OverviewSection：完成判断
OverviewSection：当前结论
```

边界：检查执行证据和逐项结果归 `验收报告`；本页只链接过去，不复制检查列表。

#### Goal History Surface

`定义目标 / 目标历史` 只保留已经完成目标和完成确认记录。

```txt
OverviewPageHeader：历史结论 / 更新时间 / 来源
OverviewSection：已完成目标
OverviewSection：完成确认
```

边界：当前目标、任务详情和下一步归各自 owner，不在历史页重复展示。

禁止：

- 用完成任务数除以任务总数计算项目进度百分比；没有当前目标验收依据时必须显示“尚未建立”，不能显示 `0%`。
- 展开活动任务列表、最近完成列表、目标范围、任务操作、风险清单、验收结果、运行日志或依据文件预览。
- 在当前进度重复展示项目概览拥有的生命周期阶段 Badge。
- 让同一功能同时归属于当前进度和其他菜单页。

### 1.5 Runbook Surface

适用：

- `项目流程 / 认识项目 / 启动方式`

结构：

```txt
OverviewPageHeader：启动结论
OverviewSection：运行环境（工作目录 / 环境要求）
OverviewSection：启动入口
```

必须包含：

- 当前项目能否启动，以及已识别的启动入口数量。
- 工作目录和从真实命令推导出的 Node/npm、Rust/Cargo、Bash 等环境要求。
- 每条命令显示标签、来源文件、完整命令和复制操作。

交互：

- 命令只能复制，不能在本页直接执行。
- 执行、进程输出和停止操作统一进入 `任务执行 / 执行终端`。
- 总体启动状态只在页头展示一次；运行环境分区不重复状态或启动入口数量。
- 每条命令以“发送到终端”为主操作、复制为次操作；发送后打开执行终端并预填命令，必须由用户确认后执行。
- 构建、测试和治理检查由任务执行链路按计划自动选择和运行，结果统一进入 `任务执行 / 执行结果`。

禁止：

- 用命令数量代替可启动性结论。
- 在没有进程管理和状态回传时增加一键启动或停止按钮。
- 从启动方式直接执行预填命令。
- 复制执行终端、工程文件预览或完整日志能力。
- 展示文件缺失、变更或过期状态；文件健康统一归 `工程资产 / 治理文件`。
- 将用户不需要手动运行的构建、测试或治理命令展示在启动方式。

### 2. Task Surface

适用：

- `任务执行 / 当前任务`
- 从 `当前进度` 点击任务后的任务详情
- `任务执行 / Patch 草案`
- `任务执行 / 执行结果`

结构：

```txt
任务标题 + 状态
返回上级入口
主操作按钮
计划摘要
影响范围
验证方式
高级详情
```

必须包含：

- 任务短标题
- 状态 badge
- 返回来源，例如 `返回当前进度`
- 主操作：`生成改动 / 应用改动 / 运行检查 / 更新交接`
- 计划摘要：做什么、看什么、改哪里、怎么验

交互：

- 任务 tab 标题必须显示任务名，不使用抽象 `执行`。
- 主操作必须首屏可见。
- 技术日志、Diff、完整检查输出放入 `高级详情`。

禁止：

- 把主要操作藏在 `更多操作` 里。
- 用内部名如 `execution`、`runner`、`patch draft` 作为用户主标题。
- 任务详情没有返回路径。

### 3. Health Surface

适用：

- `工程资产 / 治理文件`
- `项目流程 / 设计实现`
- `工程资产 / Schema`
- `工程资产 / 报告产物`

结构：

```txt
健康结论
状态矩阵：正常 / 本地变更 / 缺失 / 可能过期
建议动作
文件列表
文件预览
生成治理任务
```

必须包含：

- 健康结论
- 分类统计
- 建议处理顺序
- 可点击文件
- 可生成治理任务的动作入口

交互：

- 点击状态卡筛选文件。
- 点击文件只读预览。
- 点击生成任务进入任务闭环。

禁止：

- 只列文件路径，不说明状态。
- 把缺失、过期、本地变更混在一个列表里。
- 文件状态不可筛选。

### 4. Configuration Surface

适用：

- `Agent 配置 / 模型连接`
- `Agent 配置 / 工具白名单`
- `Agent 配置 / Skill 能力`
- `Agent 配置 / 适配器`
- `Agent 配置 / 安全边界`

结构：

```txt
可用性结论
连接 / 权限 / 能力矩阵
当前配置
不可用原因
修复动作
关联文件
```

必须包含：

- 当前是否可用
- 不可用原因
- 配置来源
- 修复或测试动作

交互：

- 模型连接可测试。
- 工具白名单可查看允许项和禁止项。
- Skill / 适配器可查看来源和能力边界。
- 不可用项可生成配置修复任务。

禁止：

- 只显示配置 JSON 或文件路径。
- 把安全边界隐藏到文档里。
- 不说明为什么不能执行。

### 4.5 Catalog Surface

适用：

- `项目流程 / 设计实现 / 界面规范 / Token`
- `项目流程 / 设计实现 / 界面规范 / 组件`

结构：

```txt
页面头部：名称 / 登记数量 / SSOT 来源
左侧内部目录：分类 / 搜索 / 当前项
右侧详情：实际预览 / 变体 / 尺寸 / 状态 / 使用页 / 源码
```

规则：

- `界面规范` 只作为分组，不渲染重复页面；Token 和组件是唯一 owner 页。
- Token 页展示实际 CSS 变量名和运行时样例，规则来源为 `docs/design/tokens.md`，运行时值来源为 `desktop/src/styles.css`。
- 组件页按 `Primitive / Pattern / Composition` 分组，优先渲染现有真实组件，不复制一套演示组件。
- 具体 Token 分类和组件条目属于页面内部目录，不登记为全局菜单。
- `查看源码` 跳转到工程文件页，组件页不复制源码浏览能力。
- 两栏目录是实际工具容器，可以有边框；详情区域保持扁平，不在卡片内继续嵌套卡片。

### 5. Memory Surface

适用：

- `知识记忆 / 项目事实`
- `知识记忆 / 用户偏好`
- `知识记忆 / 长期记忆`
- `知识记忆 / 会话摘要`

结构：

```txt
记忆类型
可信度 / 新鲜度
事实列表
来源
可沉淀项
过期项
```

必须包含：

- 信息类型
- 来源和可信度
- 最近更新时间或新鲜度
- 是否可沉淀 / 是否需要确认

交互：

- 点击来源查看证据。
- 可沉淀项生成确认任务。
- 过期项生成同步任务。

禁止：

- 把长期记忆、当前任务和对话摘要混在一个列表里。
- 未确认信息直接标为事实。

## 视觉层级

### Header

- 标题使用 `--desktop-text-title` 或现有 section title token。
- 状态摘要使用正文大小，不使用 hero 字号。
- 右侧 badge 只放当前状态，不放多个按钮。

### 指标

- 数字不得超过 `30px`，除非是单一核心评分。
- 0 值必须解释含义，例如 `0% / 任务完成度`。
- 指标卡最多 4 个。
- 指标卡可点击时必须有 hover 和 active 态。

### 列表

- 任务列表使用密集列表，不使用大营销卡。
- 每项必须有标题和状态 / meta。
- 可点击项必须有明确 hover。
- 禁用项不能看起来像主操作。

### Evidence

- 文件、报告、记录使用 chip/button 形态。
- chip 必须可点击或明确 disabled。
- 点击后在当前工作面下方展开只读预览。
- 目录和通配符必须提示不能直接预览。

## 状态规则

每个工作面必须覆盖：

| 状态 | 要求 |
|------|------|
| 默认态 | 展示真实数据和主动作 |
| 加载态 | 保留布局，显示轻量加载文案 |
| 空态 | 说明为什么为空，以及下一步 |
| 错误态 | 说明影响、原因和修复入口 |
| 只读态 | 明确“只读预览”，不出现编辑暗示 |
| 可行动态 | 主按钮可见，动作说明清楚 |
| 完成态 | 显示完成证据和下一步 |

## 验收清单

实现任何菜单工作面时，收尾必须检查：

1. 首屏是否能看出当前状态？
2. 是否有 1-3 个明确主动作？
3. 是否有可点击证据？
4. 空态是否说明下一步？
5. 错误态是否说明原因和修复入口？
6. 治理元信息是否没有喧宾夺主？
7. 是否使用 `desktop/src/styles.css` 的 token，而不是散落硬编码？
8. 是否在窄屏下不重叠、不截断关键动作？
9. 是否能从页面动作进入任务闭环？
10. 是否避免内部工程词作为用户主标题？
